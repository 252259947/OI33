# 实名认证架构检查与修正（2026-09-10）

## 结论

普通用户提交实名申请，经管理员审批通过后，即完成实名认证，不需要再走第二次旧实名审批。

认证状态、账号能否使用、教学角色和班型分别判断：实名认证不授予教练/管理员身份，也不会让用户自动加入申请填写的班型。

| 层次 | 依据 | 含义 |
| --- | --- | --- |
| 实名核验 | `oi33_enrollment.status === 'approved'` | 用户身份已经审批通过 |
| 账号使用 | `enabled`、有效期、首次改密、临时比赛范围 | 已实名账号仍可能停用、到期或仅能参加指定比赛 |
| 教学角色 | Hydro 权限、域角色，以及原有管理标记 | 控制教练、管理员操作，不来自实名申请表 |
| 作业范围 | 当前班型及作业分配 | 不由实名申请中填写的班型文本直接授权 |

没有新身份档案的原有实名用户继续兼容旧标记，不批量改写、不要求重新认证。旧管理标记 2/3 保留，不因这次修正降权。

## 本次找到的问题

### 1. 首页把开关当成数据对象

线上采用 `checkin: true`，旧首页扩展却直接向该布尔值写入认证状态和签到记录，页面拿不到这些字段后按未认证显示。这与审批是否成功不是一回事。

修正：每次请求建立独立的运势数据对象，兼容布尔开关和原有对象配置；补齐七种运势默认文本，避免抽取后出现空结果；私有数据不写回共享首页配置，响应不允许共享缓存。

### 2. 新审批与旧兼容标记可能乱序

新档案先写 `pending/approved`，再同步旧 `realname_flag`。原先没有同步版本判断：如果提交申请的同步比后续审批更晚完成，可能把已批准的旧标记改回 0。已在独立测试中确定性复现。

修正：普通用户的公共身份读取优先查询新档案；首页运势、用户展示、旧功能的共用身份检查复用这一读取。旧兼容写入增加单调版本校验，晚到的旧申请不能覆盖更新的批准结果。读取只投影用户编号与状态，不把真实姓名、学校、学号或审核意见复制进公开用户对象。

### 3. 管理员豁免不应冒充实名

极少数只有 Hydro 管理权限、没有任何实名档案或旧实名标记的账号，原页面展示申请表，但接口必然拒绝，并错误提示其已经核验。

修正：页面与接口统一说明“管理员权限不等于实名认证”，不再展示无法提交的表单，不伪造审批结果。保留不能审批自己的限制；管理员档案缺失需由另一位管理员核验处理，未扩展自助管理权限。

## 保留的流程

1. 日常用户注册后提交姓名等资料，进入等待审核状态。
2. 管理员核对资料，通过后成为已实名用户；退回需提供理由，用户可补充后重交。
3. 审批完成后，原登录会话下一次请求即可读取新状态，不要求退出重新登录。
4. 正式批量账号使用已核验名单建立档案；临时比赛账号的有效期和比赛范围继续独立限制。
5. 真实姓名仅用于本人身份页和授权教学管理，不自动公开到文章、排名和个人主页。

## 学生个人文件上传

- 学生“上传文件”按钮显示但禁用，悬停提示“没有权限”，移除原上传脚本触发标记。
- 后端 `/file` 个人存储上传也检查教学身份与 Hydro 原上传权限，不只做前端遮挡。
- 教练/管理员仍需满足原上传权限、参数和配额检查。
- 原有文件浏览、删除和题目附件接口不改变；学生文章编辑器若使用同一个 `/file` 接口上传图片，也受相同限制，已有图片不受影响。

## 验证与剩余边界

- 自动化测试覆盖申请/批准交错、兼容档案丢失或同步失败、批准后身份展示和签到读取、角色不提权、姓名不泄露。
- 独立真实 Hydro 环境验证同会话审批后首页立即出现运势按钮；学生上传请求拒绝，教师继续进入原生文件校验；不创建生产测试账号或上传生产测试文件。
- 已通过数据库只读检查确认：检查时线上已批准学生的旧标记均已同步，截图中的管理员也有原有认证标记；本次没有为这些用户补审批或改写身份。
- 历史猫咪经济模块中的部分原始数据库聚合仍直接筛选兼容标记。正常写入现在有版本保护，但若发生真实数据库写失败，这些隐藏功能仍可能短暂与权威档案不一致；未借本次修复批量迁移历史经济数据。
- 旧 `realname_flag` 仍兼具原始管理等级含义。以后如彻底移除历史经济系统，可再拆分角色与实名字段；本次不进行高风险角色迁移。
